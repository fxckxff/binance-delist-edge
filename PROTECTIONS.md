# Защиты монитора: что реализовано и как проверено

Файлы: `monitor_core.py` (логика), `monitor.py` (запуск), `selftest_monitor.py` (проверка).

Проверка: `./venv/bin/python selftest_monitor.py` → 24/24. Ни один тест не подменяет логику:
сетевые ответы подаются через `httpx.MockTransport`, но разбор, фильтры, backoff и решение
о сигнале — тот же код, что работает в бою. Два теста ходят в живой Binance.

## 1. Kill switch

`STOP`-файл проверяется в трёх точках: перед каждым шагом цикла, непосредственно перед
проверкой ликвидности и через обработчик `SIGTERM`/`SIGINT`.

```
touch ~/newsbot/STOP      # остановка в течение одного шага (< 1 c), код выхода 0
rm    ~/newsbot/STOP      # снять блокировку
```

Проверено: процесс завершился за ~1 с, в логе `CRITICAL KILL SWITCH ... graceful stop`.

**Предел:** останавливает процесс. Позиции не закрывает — потому что модуля исполнения
ордеров не существует вовсе (ключей API в проекте нет).

## 2. Backoff на 429 / 418 / 5xx / сеть

Экспоненциальная пауза 2 → 4 → 8 → 16 → 32 с (потолок 300 с), джиттер 0–1 с,
`Retry-After` имеет приоритет, после 6 попыток запрос сдаётся и цикл продолжается.

Проверено: `Retry-After: 7` → ровно две паузы по 7 с; постоянные 429 → 5 пауз с ростом,
возврат `None` без исключения; 503 и `ConnectError` — то же; HTML вместо JSON → `None`.

**Предел:** не спасает от бана по IP на уровне сети/провайдера и не меняет IP.

## 3. Устойчивость парсинга

`parse_articles()` принимает что угодно: `None`, список, строку, отсутствующий `data`,
`catalogs` строкой, `articles` со `None`/числами внутри, `title: null`, `releaseDate: "мусор"`.
Всё это даёт пустой список или запись с пустыми полями, но не исключение.

Проверено: 10 вариантов битого ответа + нормальный ответ + отсутствующий `title`.

**Предел:** если Binance переименует сами поля (`title` → `subject`), парсер вернёт пусто
и бот будет молча писать `tick: announcement list empty`. Это не падение, но и не сигнал —
нужен внешний алерт на «нет данных N минут». Сейчас такого алерта нет.

## 4. Проверка ликвидности (fail closed)

Для каждого символа из заголовка запрашивается стакан: сначала фьючерсы
(`fapi/v1/depth`), при отсутствии — спот (`api/v3/depth`). Считается номинал в USD
в полосе ±50 бп от середины. Порог по умолчанию — 5 000 USD.

Проверено: синтетический стакан даёт ровно 201.0 USD в полосе; пустой/битый стакан → 0;
живой `BTCUSDT` → 1.3 млн USD; несуществующий символ → отказ без исключения;
тонкий стакан → `SIGNAL REJECTED`.

**Предел:** глубина измеряется в момент сигнала, а не в момент ордера. Модели
проскальзывания нет. Один и тот же стакан может выглядеть глубоким и не переварить
рыночный ордер.

## 5. Синхронизация времени и отсечка старых анонсов

Смещение часов считается по `fapi/v1/time` с учётом RTT (раз в 10 минут), возраст анонса
считается уже в «серверном» времени. Анонс старше `stale_after_s = 900` отбрасывается,
анонс «из будущего» больше 120 с помечается как `CLOCK SKEW`.

Проверено: живой offset −33…+54 мс; анонс двухчасовой давности → `STALE`;
свежий анонс при измеренном смещении → сигнал.

**Предел:** это HTTP-оценка (±RTT/2), не NTP. Точность порядка десятков миллисекунд.

## 6. Персистентный курсор (без него первые пять бесполезны)

Состояние в `state/seen.json`: `bootstrapped` + до 2000 id. Первый запуск только
запоминает ленту и не выдаёт ни одного сигнала. Рестарт не повторяет старые анонсы.

Проверено: первый запуск → `bootstrap ... 0 signals`; рестарт → 0 сигналов;
новый анонс → ровно 1 сигнал.

## 7. Single instance

`flock` на `state/monitor.pid`. Второй процесс печатает ошибку и выходит с кодом 2.

Проверено: второй запуск → код 2; после освобождения блокировки запуск проходит.

## Что эти защиты НЕ решают

1. **Скорость.** Ниже — измеренные цифры, они меняют вывод.

## Измерено 30.10.2026: интервал опроса — не узкое место

| Проверка | Результат |
|---|---|
| Условные запросы (`If-None-Match`), 600/мин, 2 мин | 0 × 429, всё из кэша, медиана 16–20 мс |
| Обычные запросы каждые 15 с, 8 часов подряд | 0 × 429 |
| Обычные запросы каждые 3 с (3 процесса) | 429 (наблюдалось ночью) |
| Обход кэша (`&_=<timestamp>`) | 429 на первом же запросе, `x-cache: Error from cloudfront`, блок ~5 мин |
| `Cache-Control: no-cache`, `Pragma: no-cache`, `max-age=0` | игнорируются, ответ всё равно из кэша |
| TTL кэша CloudFront, `pageSize=1` | **111 с** |
| TTL кэша CloudFront, `pageSize=10` | **252 с** |

Эндпоинт отдаётся CloudFront. Данные в кэше живут 2–4 минуты, и клиент не может
потребовать свежие: обход кэша блокируется на уровне WAF, клиентские cache-заголовки
игнорируются. Значит опрос раз в 1 с вместо 15 с выигрывает в среднем ~7 с, а не 13.

Что это делает с эджем (из `data/announcement_latency.json`, n=77, выход на 300 с):

| вход через | медиана, бп | доля выше cost 4 бп |
|---|---|---|
| 1 с | 240.6 | 73% |
| 5 с | 132.4 | 69% |
| 30 с | 110.6 | 64% |
| 60 с | 40.9 | 64% |
| 300 с | 0.0 | 0% |

При TTL 111–252 с ожидаемый лаг обнаружения ~60–130 с. То есть реальная медиана —
порядка 30–40 бп за сделку, а не 240. Эдж остаётся положительным, но тонким.

Прибор для проверки: каждый новый анонс пишется в лог как `NEW id=... detect_lag=...s`.
Через несколько недель это даст фактическое распределение лага вместо оценки.

2. **Исполнение.** Ордеров нет вообще: ни бумажных, ни реальных. `SIGNAL PAPER` — это строка
   в логе, а не сделка.
3. **P&L.** Ни одна цифра доходности этим кодом не измерена.
4. **Алерты.** Нет уведомлений: если бот упадёт или API замолчит, узнаешь только по логу.
